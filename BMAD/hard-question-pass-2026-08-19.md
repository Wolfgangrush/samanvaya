### 1. WHAT WILL BREAK?

1.  **The upstream India adapter (`.india.adapter`) breaks silently.** The architecture explicitly forbids reimplementing India logic (`dpdp-law-to-code`) and pins the package. If the upstream maintainer changes the `ComplianceResult` shape or modifies a `check_*` function signature (e.g., adding a required argument), the current architecture only detects this via the adapter's unit tests, which depend on specific fixture shapes. The tool will not flag this as a runtime `[FACT NEEDED]` error; it will likely throw an opaque `ImportError` or `TypeError` deep within the adapter code during the `pack.india` evaluation. The "hard invariant" (consume unmodified) creates a single point of failure that requires manual intervention to unpin and update, violating the "offline, autonomous" usage goal if the adviser is blocked by a dependency mismatch.
2.  **`JurisdictionResolver` creates false positives for US/Canada federal-only entities.** The resolver forces sub-nationals (states/provinces) to be specified to avoid a `gap`. However, for a small organization that triggers only HIPAA (federal) and has no physical presence in a CCPA state, the declaration "US" with *no* states should result in `satisfied` for HIPAA and `does_not_exist` for California. Instead, the design flags the entire US regime as `gap` (or emits a spurious `OTHER` gap) because the tree is "incomplete." The tool fails to distinguish "incomplete footprint" from "no footprint in that state," forcing the user to list 50 states to "prove" they aren't in California.
3.  **The `sub_unit` primary key collides on overlapping US State/Federal obligations.** The architecture treats `(regime, sub_unit)` as a tuple for routing. For a California hospital, both CCPA (`US-CA`) and HIPAA (`US-FED` or `None`) apply. If the `Obligation` model defines `regime` as `US` and allows `sub_unit` to be `US-CA` for state law and `None` for federal, the design is sound. However, the "Jurisdiction as a tree" section lists the federal sectoral layer as distinct items (HIPAA, GLBA) but the `RegimeId` enum only has `US`. If the `US` pack emits a `BREACH_NOTIFICATION` obligation for HIPAA (federal, 500 patients) and another for CCPA (state, any resident), and both carry `regime="US"`, the `Per-regime rollup` will either merge them into one row (losing the "trigger" distinction) or duplicate the row in a way that makes the `regime` grouping ambiguous. The model needs `instrument` as part of the grouping key to avoid this collision.
4.  **`sub_topic` string concatenation is not comparable.** The design relies on `(topic, sub_topic)` as the comparison key for the `DeltaComputer`. It defines `sub_topic` as opaque strings like `age_threshold_<N>`. If the India pack emits `age_threshold_18` and the EU pack emits `age_threshold_16`, these are distinct strings. If the EU pack emits `age_threshold_<16>` (range), the strings don't match. If the Singapore pack emits `age_threshold_18_with_consent`, the delta computer reports 3 distinct rows where there is actually 1 concept (Children). The delta will fail to "summarize" divergences and will instead list a combinatorial explosion of "string mismatches" that the adviser must manually reconcile, defeating the purpose of the delta layer.

### 2. WHAT EDGE CASES ARE WE MISSING?

1.  **Non-contiguous statutory applicability (The "Phased In" Edge Case).** The architecture handles `in_force_from` (date) but assumes "applicable" is binary once the date is passed. However, laws like PIPEDA or the UK GDPR have applicability thresholds (e.g., "organizations with >250 employees" or "processing that poses a high risk"). The `Declaration` has an `employee_count` field, but the `Obligation` model lacks a `thresholds` field to store the criteria. The engine cannot emit `not_applicable` for a small business if the pack cannot encode "This obligation only applies if `employee_count > 250`". The pack will either incorrectly flag a gap or falsely satisfy the obligation for a small entity.
2.  **Conflicting Legal Basis within a Single Purpose.** The `Purpose` model allows a single `legal_basis`. In the US (CPRA), a "Sale" of data might require "Opt-Out" consent, while in India (DPDP) the same "Sale" requires "Explicit Consent". A user declaring "Processing: Sale" cannot satisfy both in one `Purpose` entry. The design assumes a mapping from `Purpose -> Basis` but does not support the case where a single purpose triggers *two* conflicting bases in two regimes. The user must split this into two purposes ("Sale for US" and "Transfer for India"), but the schema does not enforce or guide this, leading to a finding where `result=satisfied` for EU but `result=gap` for India on the same row.
3.  **"Safe Harbor" logic is impossible without conditional outcomes.** The architecture allows `result` to be one of 5 enums. It does not allow conditional logic: "Satisfied IF `security_safeguards.encryption == 'AES256'` AND `recipient.country == 'FR'`". If the declaration claims "Encryption: Yes" (generic) and the statute requires "Encryption: AES-256" (specific), the tool can only emit `satisfied` (if it accepts the generic) or `contested` (if it demands the specific). It lacks the internal structure to evaluate the *value* of a safeguard against the *value* required by law, reducing complex control requirements to boolean checks.
4.  **The "Consent Manager" Deadlock (Self-referential compliance).** India requires a "Consent Manager" to be appointed if you are a "Significant Data Fiduciary". The appointment of a manager is an obligation. Being an SDF is a status based on volume/processing. The `Obligation` for "Appoint Manager" applies *only* if the organization is an SDF. The `Obligation` for "Determine if SDF" applies to everyone. The engine cannot chain evaluations (Output A becomes Input for B). The pack must make a unilateral decision on the SDF status based on the declaration, but if the declaration is ambiguous, the "Appoint Manager" finding oscillates between `gap` and `not_applicable` depending on how the pack guesses the SDF status, creating unstable reports.

### 3. WHAT IS OVER-ENGINEERED?

1.  **The `DeltaComputer` and the `Divergence` model.** The delta layer is the most complex part of the architecture (grouping by tuple, comparing opaque strings, "strongest obligation" algorithms). For a tool whose primary output is a list of obligations and gaps per regime, the "cross-regime comparison" is a secondary feature. A simpler approach is to output the six independent `RegimeRollup` objects (JSON) and let the human (or a spreadsheet) perform the delta. The machine generation of the delta creates a massive maintenance burden (ensuring `sub_topic` strings match across 5 distinct codebases) for a feature ("strongest obligation") that is legally dangerous (the tool cannot legally advise on which standard is "strongest" without engaging in legal interpretation).
2.  **The `OfflineVerifier` / `socket` import hook.** The PRD enforces offline as a "hard constraint," but the implementation (monkey-patching `socket` at runtime) is fragile and complex. A better enforcement is the environment: "The tool assumes an air-gapped network." The attempt to *programmatically* verify the network posture adds unnecessary code and attack surface (the checker itself) without guaranteeing that a transitive dependency isn't making a network call via a C-extension that bypasses the hook. The requirement should be satisfied by "No dependencies require a network" (checked at install/audit time) rather than a runtime syscall guard.
3.  **The `PackInfo` `draft` flag and the `PackRegistry` discovery mechanism.** The architecture uses setuptools entry points to discover packs and includes metadata like `version`, `as_at`, and `draft`. This is a plugin system pretending not to be one. For v1, there are exactly six packs, all first-party. Using a dynamic registry adds indirection (loading entry points, checking metadata, refusing to load draft packs) that makes the code harder to read and debug. A hardcoded list of regimes (or a simple dictionary mapping `RegimeId` to the pack class) is sufficient. The "extensibility" to third-party packs is rejected scope for v1, so the infrastructure for it is over-engineered.
4.  **`ruamel.yaml` for "Round-trip" editing.** The requirement that the tool preserves comments and key order so the adviser can "diff" the declaration implies the tool *writes* back to the declaration. But the PRD explicitly says the tool "does not patch the declaration" and is offline/read-only. The tool reads the declaration and writes a *report*. Using `ruamel.yaml` (instead of standard PyYAML or strict JSON) introduces a heavy dependency with a complex API just to preserve formatting that the tool never outputs. If the tool doesn't modify the input file, it doesn't need to round-trip it. Standard parsing is sufficient.
