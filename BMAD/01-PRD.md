# 01 — PRODUCT REQUIREMENTS  ·  samanvaya

**Date:** 2026-08-19 · **Owner:** the maintainer · **Filter:** see `06-FILTER.md` (run AFTER the code exists)

## What we are building

An offline, declaration-driven privacy conformance tool that reads a human-authored description of an organisation and, against that single declaration, reports which obligations are present, missing, or contested under six named regulatory regimes — without ever touching the organisation's systems, networks, or data. The tool is jurisdiction-aware but jurisdiction is a tree, not a flat list, because the United States and Canada have binding sub-national law that must be enforced alongside the federal layer.

## Who it is for

A solo data-protection adviser in India, sitting in front of a laptop with a terminal open and a folder containing a client's self-declared privacy dossier (a JSON or YAML file written by the client or by the adviser from a discovery interview). On their screen: a single CLI command, a list of the six regimes with their sub-units expanded, and a finding per rule that either cites the named instrument and provision that is satisfied or names the gap with the same citation in the "expected" position. The adviser reads the findings, drafts a memo for the client, and bills for the judgement. The tool is not on the screen again until the next dossier.

## What it must do

1. Accept a single declared input file (JSON or YAML) describing one organisation: its legal form, the jurisdictions in which it processes personal data, the categories of data it handles, the purposes, the recipients, the security safeguards declared, the consent mechanism declared, the breach workflow declared, the data-subject-request workflow declared, the retention periods declared, and any sub-national units (US states, Canadian provinces) it operates in.
2. For the India rail, consume `dpdp-law-to-code` (MIT, github.com/Wolfgangrush/dpdp-law-to-code, 407 passing tests) as the India checking engine and invoke its existing `check_*` functions against the declared input; do not reimplement India.
3. For each of the five non-India regimes — General Data Protection Regulation (Regulation (EU) 2016/679), UK GDPR as retained and as amended by the Data (Use and Access) Act 2025, the ~20 US state comprehensive statutes active in 2026 (California CCPA/CPRA, Colorado, Connecticut, Delaware, Florida, Indiana, Iowa, Kentucky, Maryland, Minnesota, Montana, Nebraska, New Hampshire, New Jersey, Oregon, Rhode Island, Tennessee, Texas, Utah, Virginia) plus the federal sectoral layer (HIPAA, GLBA, COPPA, FERPA), Singapore Personal Data Protection Act 2012 (as amended 2020), and Canadian PIPEDA plus Quebec Law 25 — evaluate the declared input against the obligations those instruments impose, treating US and Canada as jurisdictional trees so that sub-national law is enforced whenever the declared jurisdictions include that sub-national unit.
4. Emit, for every obligation evaluated, a structured finding carrying: the regime, the sub-national unit (if any), the named instrument, the exact section or rule number that is the source of the obligation, a one-line statement of what the obligation requires, a one-line statement of whether the declaration satisfies it, and a citation pointer the human can verify against the primary source.
5. Produce a per-regime summary rollup and a single consolidated report covering all six regimes, with the India findings sourced verbatim from `dpdp-law-to-code`'s `ComplianceResult` so the existing 407 tests continue to attest the India rail.
6. Carry, on every artefact it emits, the disclaimer that the output is not legal advice and is a conformance report only.
7. Run entirely offline. No network calls. No telemetry. No outbound HTTP of any kind at runtime.

## What it must NOT do — banned scope

This section is load-bearing. It is what gets pointed at when scope creeps at hour six, and what the later `06-FILTER` sweeps against. Anything listed here is deferred, not debated mid-build.

- **No database connectors of any kind.** No connection strings, no DSNs, no JDBC URLs, no `psycopg2.connect`, no `mysql.connector`, no ODBC, no Mongo URIs, no SQLite paths to a client database. The tool receives a declared file. It does not reach into a datastore. Reason: the author is a practising advocate; touching client personal data would make him a Data Fiduciary or Data Processor in his own right under the DPDP Act 2023, with his own breach-notification duty and indemnity exposure.
- **No credentials, secrets, API keys, cloud roles, or service principals.** No AWS access keys, no Azure client secrets, no GCP service account JSON, no OAuth tokens, no SSH keys, no `~/.aws/credentials` reads. The declaration must be hand-authored and contain no live credentials. Reason: same as above — possession of credentials to a client's environment creates fiduciary status and breach exposure.
- **No network scanning, port scanning, or service discovery.** No `nmap`, no `masscan`, no SNMP walks, no SMB enumeration, no cloud metadata endpoint queries (`169.254.169.254` and equivalents), no Shodan calls, no DNS brute-forcing, no subdomain enumeration. Reason: scanning is a different industry and a different legal posture; this is a conformance tool, not a scanner.
- **No discovery by scanning, crawling, or probing.** No web crawler, no sitemap parser, no headless-browser rendering of client pages to scrape cookies and forms, no API endpoint fuzzing, no static analysis of a client's deployed application. The declaration is the input; it must be written by a human who has spoken to the client. Reason: the tool is for advisers who have already done the interview, not for automated reconnaissance that would itself be a processing activity.
- **No implementation or testing of security controls.** The tool may check whether the seven items in Rule 6(1) of the Digital Personal Data Protection Rules 2025 are DECLARED. It may not generate encryption code, configure a key management system, set up access controls, write IAM policies, test for SQL injection, run a vulnerability scan, or perform a penetration test. Reason: implementation and testing are a CISO service, not a conformance check, and would convert the author into a Processor.
- **No legal advice.** The tool reports conformance findings against named statutory provisions. It does not opine on whether a client "should" do something, does not predict enforcement outcomes, does not draft contract clauses for the client, does not advise on litigation strategy, does not opine on cross-border transfer mechanisms beyond citing the relevant rule. Every artefact carries the disclaimer. Reason: a tool cannot practise law. Output that reads as advice to a person who is not the adviser's client creates liability without a retainer, and an enrolled advocate's public tool emitting advice engages Bar Council of India professional-conduct rules. The advocate advises; the tool reports.
- **No hosted multi-tenant SaaS in v1.** No shared backend, no per-tenant database, no per-tenant API keys, no per-tenant billing, no web UI with login. The tool is a local CLI that runs on the adviser's machine against a local file. A future v2 may add a single-tenant self-hosted mode, but never a vendor-hosted multi-tenant service. Reason: a hosted service would receive client declarations containing client personal data and would make the operator a Data Fiduciary or Processor with breach-notification duties under the DPDP Rules 2025.
- **No web UI in v1.** No browser frontend, no React/Vue/Svelte app, no server-rendered HTML with client data, no Tailwind, no admin dashboard. v1 is CLI only. Reason: a web UI invites hosted deployment, session storage of client data, and accidental persistence — all of which create fiduciary exposure.
- **No storage of client personal data.** No retention of the input declaration beyond the run, no log of findings persisted to disk by default, no analytics on usage, no crash reports containing input data. Reason: retention of client data makes the tool a Data Fiduciary or Processor.
- **No copying of source code from any other privacy tool.** No reading of any other privacy tool's source code, no vendoring of any other privacy tool's source code, no translation of any other privacy tool's logic into this codebase. The Ethyca Fides and fidesops projects are Apache-2.0; the Privado project is LGPL-3.0 and must never be vendored or linked. Public interchange formats may be implemented from their published specifications; source code may not be copied. Reason: the clean-room posture is the legal foundation of the tool's own licence; copyleft contamination would destroy it.
- **No invention of statutory references.** Every citation must point to a named instrument and a section, rule, or schedule that exists in the Verified Facts Brief supplied to this PRD. If a citation cannot be sourced from the brief, the tool must emit `[FACT NEEDED: <question>]` and stop rather than guess. Reason: a guessed section number in a legal-output tool is malpractice.
- **No auto-remediation.** The tool reports gaps. It does not patch the declaration, do a "best-effort fill", suggest boilerplate text to drop in, or run a "fix" mode. The adviser writes the remediation memo; the tool stays out of that loop. Reason: auto-remediation drifts into legal advice and into drafting, both of which are out of scope.
- **No ingestion of the client's own logs, audit trails, ticket exports, or HR records.** The declaration is a hand-authored summary, not a dump of operational artefacts. Reason: ingesting those artefacts would be processing of personal data at scale and would convert the operator into a Processor.
- **No reimplementation of the India rail.** The India checking logic lives in `dpdp-law-to-code`; this tool consumes that package and calls its `check_*` functions. It does not reimplement Rule 6(1), Rule 7, Rule 13, or any other India provision. Reason: 407 tests already attest the India rail, and reimplementation would fork correctness.
- **No jurisdiction flattening.** The tool must not treat the United States as one regime or Canada as one regime. Both are trees. Treating them as flat lists is a known scope-creep vector and is forbidden. Reason: sub-national law is binding; flattening produces false negatives.
- **No use of the names "US GDPR", "Singapore GDPR", or "Canada GDPR".** These names do not correspond to any instrument. The tool must use the correct names: General Data Protection Regulation for the EU, UK GDPR (as amended) for the UK, the named state and federal statutes for the US, Personal Data Protection Act 2012 for Singapore, and PIPEDA / Quebec Law 25 for Canada. Reason: misnaming instruments is a category error that propagates into citations.
- **No published output on the tool's say-so.** The tool produces a report file. It does not email it, post it, upload it, file it with a regulator, or send it to a client. The adviser decides what leaves the adviser's machine. Reason: the operator must not become the channel through which client disclosures reach third parties.

## Inputs

| source | where from | format | how often |
|---|---|---|---|
| Organisation declaration | Hand-authored by the adviser or by the client under the adviser's instruction, derived from a discovery interview | JSON or YAML, single file per organisation | Once per engagement; re-run when the declaration is amended |
| `dpdp-law-to-code` package | github.com/Wolfgangrush/dpdp-law-to-code (MIT) | Python package import | Pinned at install; updated by the adviser when a new release of the upstream package is reviewed |
| Statute text | Primary sources: Gazette of India Extraordinary for the DPDP Rules 2025 (G.S.R. 846(E), 13 November 2025); EUR-Lex for Regulation (EU) 2016/679; legislation.gov.uk for the Data (Use and Access) Act 2025 and the Data Protection Act 2018; state legislative sites for US state statutes; the PDPA 2012 (as amended 2020) on Singapore Statutes Online; PIPEDA on the Justice Laws Canada site; Quebec Law 25 on the Publications du Québec site | Plain text or HTML, referenced by citation, not loaded at runtime | Static; the tool does not fetch statute text at runtime |
| HIPAA / GLBA / COPPA / FERPA text | Primary US federal sources (govinfo.gov, eCFR) | Plain text or HTML, referenced by citation, not loaded at runtime | Static |

## Outputs

| artifact | where to | schema | consumed by |
|---|---|---|---|
| Per-finding record | Local stdout and/or a local file written to a path the adviser chooses | `regime`, `sub_unit` (nullable), `instrument`, `provision`, `obligation_summary`, `declaration_summary`, `result` (one of `satisfied`, `gap`, `contested`), `citation_pointer` | The adviser, who reads it and drafts a memo; no machine consumer in v1 |
| Per-regime rollup | Same local file, a section per regime | Counts of `satisfied`, `gap`, `contested`, with the per-finding records nested | The adviser |
| Consolidated report | Same local file, single document, regimes in order | All per-regime rollups plus a header carrying the disclaimer, the date, the declaration's hash, and the tool version | The adviser; the adviser decides what, if anything, is shared with the client |
| India findings | Sourced verbatim from `dpdp-law-to-code`'s `ComplianceResult` | As defined by the upstream package | The adviser; the upstream package's existing 407 tests attest these |
| Disclaimer | Carried on every artefact | Fixed string: that the output is not legal advice and is a conformance report only | Every reader |

## Constraints that are not negotiable

- **Declaration, never connection.** The tool accepts a declared description of an organisation as a file. It does not accept a database connection string, a credential, an API key, a cloud role, or any network connector. The author is a practising advocate; touching a client's personal data would make him a Data Fiduciary or Data Processor under the Digital Personal Data Protection Act 2023 with his own breach-notification duty and indemnity exposure under Rule 7.
- **Clean room.** The tool does not read another privacy tool's source code. Every check traces to a section or rule of a named instrument — never to anyone's codebase. Public interchange formats may be implemented from their published specifications; source code may not be copied. Ethyca Fides and fidesops are Apache-2.0 (permissive); Privado is LGPL-3.0 (copyleft) and must never be vendored or linked.
- **Not legal advice.** Every output carries the disclaimer. The tool reports conformance findings; it does not advise.
- **No scanner, no control implementation, no CISO service.** Checking whether the seven Rule 6(1) minima are declared is in scope. Implementing or testing them is out of scope forever.
- **The tool must consume `dpdp-law-to-code`, not reimplement India.** The upstream package already encodes DPDP Act ss.5-16 as ~50 `check_*` functions with 407 passing tests. The new tool calls them and surfaces their `ComplianceResult`. It does not duplicate the logic.
- **Every finding must carry a citation to a named instrument and a provision.** No finding may be emitted without a `regime`, `instrument`, and `provision` field. If a required citation cannot be sourced from the Verified Facts Brief, the tool emits `[FACT NEEDED: <question>]` and stops for that finding rather than guessing a section number, rule number, date, threshold, or deadline.
- **No output may be published on the tool's say-so.** The tool writes a local file. It does not email it, post it, upload it, or file it. The adviser chooses what, if anything, leaves the machine.
- **Offline.** No network calls at runtime. No telemetry. No outbound HTTP. The absence of network calls is verifiable at the syscall level.
- **Jurisdiction is a tree.** The United States and Canada are enforced as country -> sub-national unit trees. A declaration that names "United States" without naming sub-national units is incomplete; the tool reports the gap rather than assuming coverage.
- **Open source.** The tool ships under a licence compatible with consumption of `dpdp-law-to-code` (MIT-compatible) and incompatible with copyleft contamination (no LGPL/ GPL inbound, no AGPL outbound by default). The exact licence is fixed in `02-ARCHITECTURE`.

## Done looks like

On a freshly cloned machine with only Python and the declared input file present, running the tool's single CLI command against the input produces a local report file in which every finding carries a named instrument and provision, the India findings are bit-identical to the `ComplianceResult` records produced by `dpdp-law-to-code`'s own test suite, and the report header carries the not-legal-advice disclaimer — and nothing leaves the machine.
